Annex 2 — Security measures

In place

  • Encryption in transit: TLS on every connection from the internet, with certificates issued per host. Traffic between our servers runs over a private network inside one datacenter and is not separately encrypted.
  • Encryption at rest, for payloads: recorded request bodies, outbound responses and message payloads, the replicated write log, and store values written under shredKey are encrypted with AES-256-GCM under per-app keys (or per-person keys the app names). Key files are themselves encrypted under a cluster key.
  • Erasure by key destruction, per person (shredKey.destroy) and per app (on deletion).
  • Isolation: each app has its own replicated store, its own storage prefix, its own keys, and a fresh JavaScript context for every request; session cookies are scoped to a single host.
  • Resource limits: per-request time and memory limits; automatic pausing of apps that repeatedly exceed them.
  • Outbound controls: outbound requests cannot reach private, loopback, link-local or metadata addresses; they are rate-limited per plan and off on the free plan.
  • Minimisation: client IPs masked by default; header values recorded only when read; response bodies not recorded.
  • Replication: every write is stored on a majority of three servers before it is acknowledged.
  • Access: production access is limited to our operators; customer-facing access goes through sign-in by email link, with link tokens stored hashed.

Not in place — stated so you can judge

  • Request-record fields other than payloads — paths and query strings, header values, store values the handler read, console output, exception messages, tags — store values not written under shredKey, store key names, code and static files are not encrypted by us, and we do not request encryption from our storage provider. Key destruction therefore does not reach them.
  • All three servers are in one datacenter: replication protects against a server failing, not against the site failing.
